# ESP-VISION capabilities

Choose only the capabilities needed for the user's request. Use the `esp-vision-knowledge` MCP for authoritative ESP-VISION APIs, chip support, firmware guidance, and examples. Use the bundled CLI for local device discovery, inspection, configuration, control, firmware operations, Python execution, files, captures, watches, or batch plans. A documentation question does not require a device connection; a device operation does not require a documentation lookup unless an API or firmware detail is uncertain.

Knowledge MCP provides documentation; device operations intentionally use the local CLI. An absent Device MCP entry is not an installation defect or a reason to add a wrapper. Check official knowledge against the actual board and firmware before claiming hardware API or live-capture support. Package versions alone do not establish payload identity, and an exported package does not establish host activation or marketplace approval; see the application workflow reference below for support checks.

Invoke the installed plugin copy with Node and the absolute path to `cli/device-cli.mjs`. Locate the current installed Skill through the host; the plugin root is two directories above the `skills/esp-vision-development` directory. Verify the CLI exists there and set the current shell variable CLI to that absolute path, quoting paths with spaces. Resolve paths from this installation, not the user project. Plugin-root substitution in host configuration is not a guaranteed environment variable in arbitrary terminal sessions. If resources are absent, report installation failure. Do not invoke a global CLI, npx, or a separate Device MCP server. The standalone `@esp-vision/device-cli` package remains available outside this plugin.

Use `node "${CLI:?Set CLI to the verified installed bundle path}" --help` for command syntax. For serial-adapter failures, npm native-backend availability, shell rewriting of device paths such as `/models`, or host permission/classifier blocks, read the Troubleshooting Q&A in [application workflow](references/application-workflow.md) before retrying; explain task-relevant diagnostics and request the host's native authorization when required. On Windows, prefer PowerShell for device paths. In Git Bash/MSYS, keep device paths unchanged with a command-local `MSYS2_ARG_CONV_EXCL='*'` prefix and use verified Windows paths for the CLI and local input/output files; do not strip drive letters to guess a device path. Treat shell path rewriting as a hypothesis until the received arguments establish it. Inspect candidates without probing when discovery is needed. Select a serial path or TCP endpoint explicitly; never choose one automatically. Before a requested device change, inspect the selected device when identity or firmware capabilities matter. Keep device-specific claims grounded in the connected device or the official Knowledge MCP.

Before every firmware-specific Knowledge lookup, automatically match the selected device's version. Run the bundled CLI `inspect --port <selected-port> --fields identity --json` (or `--tcp <selected-endpoint>`), then read `result.identity.firmwareVersion` from its successful JSON envelope. The bundled [knowledge-version helper](scripts/knowledge-version.mjs) accepts that envelope on stdin and returns the exact `{ "firmwareVersion": "..." }` arguments; it performs no device I/O. Use this helper with Node to validate the selection, and merge its result into every `get_api`, `get_capabilities`, `search_docs`, `list_modules`, `list_symbols`, `get_example`, `list_examples` and `get_concept` request. Call `list_firmware_versions` to verify that exact version is available. Do not use Plugin, CLI, Core or Knowledge npm versions as firmware versions. Re-inspect after flashing, reconnecting or switching devices; never carry a previous device's selection into another device's queries.

If the device is unavailable or the question is offline, ask for an explicit target firmware version first. If the version is missing, unknown or absent from `list_firmware_versions`, explain the limitation and offer to update to official firmware. Wait for the user's choice.

Only after the user explicitly declines the firmware update, use the latest available official firmware Knowledge snapshot: pass the decoded JSON object from `list_firmware_versions` (its `latestFirmwareVersion`, `firmwareVersions` and `snapshots` fields) on stdin to `node scripts/knowledge-version.mjs --declined-firmware-update` from this Skill directory, and merge the returned `firmwareVersion` and `snapshotVersion` into every content request. The helper uses the catalog-maintained `latestFirmwareVersion` and its active snapshot, without inferring release order from date or semantic-version TAG spelling; it pins concrete versions, never the string `latest`. Explain the selected Knowledge version and that its APIs may differ from the device. This choice applies only to the current device and task; ask again after switching devices, reconnecting or flashing. If the user chooses to update, complete the separately authorized official firmware workflow, re-inspect, and match again. Silence, a timeout or a failed update is not a decline. Never silently fall back to latest or the nearest release. If the catalog is unavailable or has no official snapshot, report that error and stop rather than guessing.

Preserve development suffixes verbatim; do not strip `-dirty`, commit suffixes or a leading `v` to make a version match. Only the exact catalog identity establishes a match. `server_info` describes the runtime/catalog, not a default firmware. Tool results return `{snapshot,result}` and include `_meta.knowledgeSnapshot`; verify the visible snapshot firmwareVersion (and snapshotVersion when pinned) matches the selected query arguments, including a user-approved fallback, and retain snapshotVersion when reproducible answers are needed. Versioned module resources use `esp-vision://firmware/{firmwareVersion}/module/{name}` (or `/snapshot/{snapshotVersion}/module/{name}` after the firmware segment).

Each CLI operation connects to the selected device and disconnects in cleanup when the operation finishes. Inspection, capture, watch, configuration and native file uploads use a connection that does not probe or interrupt the Python REPL. Python execution and REPL-backed file operations can interrupt an existing program; use them only when that interruption is intended. `watch` keeps the connection for its requested duration and disconnects on completion or cancellation. If another tool or client currently owns the device, do not force takeover or retry blindly; ask that owner to stop and release its session before starting a CLI operation. After the CLI command ends, wait for its cleanup and verify the result before handing control to another owner.

Use `--json` when structured output helps. The CLI writes one versioned JSON envelope to stdout; status, progress, Python output, and diagnostics are NDJSON on stderr. Binary reads and captures write to the requested local file and return metadata. For batch plans, report which operations completed and which failed.

Cancellation releases the local connection but does not undo device changes or prove that a started script stopped. A timeout, cancellation, lost response, or unknown execution result can leave a side effect uncertain. Inspect the device state before retrying; do not repeat a command whose outcome is unknown. Follow the user's requested target and authorization, and ask only when the endpoint, board, or requested side effect cannot be determined safely.

For a continuous application, upload its script and dependencies before starting it with `python --path <device-path> --completion start`, without `--timeout`. A successful start result confirms that the VM entered the script runner; it does not prove application initialization or later execution succeeded. Use passive captures while the app runs, then `control --action stop` (without `--mode`), then read progress files. `files list/read/remove/mkdir` and Python REPL commands can interrupt the running app. For installation support, hardware capability checks, continuous applications or camera/LCD acceptance, read [application workflow](references/application-workflow.md) for the relevant checks and evidence criteria.

Python stdout is bound to its original EV-MUX session: a new `watch` cannot reattach to a previous session's Python output. Use foreground `python --completion wait` when live Python output is required; a bounded `watch` observes events and diagnostics available to its current session. Inspection fields `runtime.scriptRunning` and `runtime.run` track execution initiated by the current SDK session; a new CLI process cannot use them to determine whether a detached device program is running. `runtime.vmReady` means the VM has started, not that it is idle. Preserve application cleanup handlers and explicitly stop a running application before replacement.

When development exposes a reproducible official package, tool, firmware or knowledge problem, retain a brief local feedback note: requested outcome, versions, minimal commands, expected/observed results, relevant evidence, workaround and what remains unverified. Distinguish confirmed defects from supported constraints and application mistakes. Use available facts and mark missing details unknown; do not make the user fill gaps before recording the report. Continue the original task when a workaround permits it.

Report confirmed functional problems only through https://github.com/espressif/esp-vision/issues. Search existing issues first and prepare an English GitHub issue draft using the appropriate repository issue template, including the local evidence note above. Show the proposed issue and attachments and obtain explicit user authorization before submitting or uploading anything; the user may keep the draft without submitting it. Knowledge MCP is read-only documentation lookup, not an issue-reporting or anonymous-feedback channel; do not look for or invoke submission tools through it. If GitHub submission is unavailable, provide the draft and https://github.com/espressif/esp-vision/issues/new/choose for manual submission. Never include credentials or silently upload logs, images or bug reports. For suspected security vulnerabilities, follow the repository's [SECURITY.md](https://github.com/espressif/esp-vision/security/policy) private-reporting instructions instead of a public issue.

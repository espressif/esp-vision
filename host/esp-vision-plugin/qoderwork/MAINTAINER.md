# QoderWork candidate preparation

Reference checked on 2026-10-27: [QoderWork extension release guide](https://docs.qoder.cn/qoderwork/user-guide/qoderwork-extension-release-guide-skill-plugin-connector). Its `.md` variant is downloadable. This is the QoderWork format; the separately documented Qoder IDE/CLI plugin schema is not evidence that QoderWork accepts every CLI field or marketplace installation command.

For a source-checkout candidate matching CI, first run `node tools/ci/mcp/install_host.mjs --output <absolute-project-local-artifact-directory>` from the repository root. This stages the current Device Core source without changing the tracked registry lock. A registry dependency with the same npm version can contain older code and is not evidence of matching source. Build the normal plugin CLI closure next (`npm run build` in `host/esp-vision-plugin`), then run `npm run build:qoderwork -- --output-dir <absolute-artifact-directory>` with an output directory outside the plugin source. Set TMPDIR/TMP/TEMP under `/home/libo/project/.esp-vision/`. `npm test` includes the QoderWork ZIP roundtrip, unchanged CLI/license bytes, independent ZIP CRC/extraction and extracted CLI help checks. The script does not install, upload, submit or publish anything. The new adapter is a maintainer-side artifact builder; npm package name/version, its files allowlist and legacy installers remain unchanged.

The plugin manifest and Skill versions are independent source-controlled `qoderwork/plugin.json` metadata; use three-part numeric semver and increment it for each public release. Initial candidate version is 0.1.0. `BUILD-PROVENANCE.json` uses the strictly validated full `CI_COMMIT_SHA` in CI without requiring Git; local builds fall back to Git. It stores the source commit, npm source version and payload digests, while a sidecar SHA-256 binds the actual ZIP. Build a release candidate from a clean committed tree. Retain the tested ZIP unchanged for any later authorized submission.

The Work guide requires a manifest, metadata, embedded Skills and role instructions, but does not publish a full JSON schema or example manifest. The minimal manifest uses name, displayName, version, description, author, homepage, repository, license, keywords, skills and mcpServers; actual acceptance of these fields remains a client-precheck item. The role uses the explicitly listed `qoder.md` file; no speculative Agent frontmatter, model IDs, runtime variables, Connector IDs, market IDs, OAuth tokens or IDE-specific host settings are generated.

The MCP setup follows the guide's documented `{{USER_CONFIG}}` form. The guide does not explicitly document fixed anonymous URLs as an exception, so a constant URL optimization awaits QoderWork confirmation. The user copies the public official Knowledge URL, not a credential. The homepage link is informational and does not provision a personal address. See CONNECTORS.md for the unresolved relation between declarative MCP setup and the requirement that referenced market Connectors already be published.

Before submission, capture actual QoderWork version and structure-precheck result; verify metadata import, installed CLI/resources, role/Skill activation, official Knowledge MCP setup/tool use, and user-authorized device operations/cleanup. Record observed results and exact ZIP digest. The suggested example prompts in the packaged README are a test plan, not completed platform tests. Confirm the intended publisher account and market dependency handling in the client. Then submit as Plugin through “我的发布 → 提交新拓展” only when authorized; machine review, possible human sampling and approval are separate states. No portal activation or marketplace approval has been obtained by local checks.

## Attach the package to a repository release

QoderWork currently exports CI artifacts only; there is no automatic QoderWork registry/Release publication job. On the intended protected release tag, wait for `plugin_checks` and the firmware/release qualification jobs to succeed, then download `.cache/qoderwork-plugin/esp-vision-qoderwork-<plugin-version>.zip` and its `.sha256` from that tag pipeline. Verify the checksum and that the embedded `BUILD-PROVENANCE.json.sourceCommit` equals the tag commit. Do not rebuild the tested ZIP or substitute an MR candidate after source history changes.

Upload the verified ZIP and checksum to the project's Generic Package Registry under package `esp-vision-qoderwork`, using the immutable firmware tag as the registry version. The registry version is independent of the embedded QoderWork semver: never reuse `0.1.0` as a registry key for different source builds. Preserve existing identical bytes and reject conflicting bytes; read back both uploads before adding their canonical URLs as package links under the existing GitLab Release's assets. Keep the release notes and other assets. CI artifact links expire after one month and are not durable release attachments.

WorkBuddy Expert has a separate automatic `publish_workbuddy_expert` job gated by protected firmware release qualification; it publishes its checked ZIP, checksum and receipt. Neither attaching repository release assets nor merging these changes submits to the QoderWork/WorkBuddy marketplaces or publishes npm. Before a public QoderWork marketplace update, increment `qoderwork/plugin.json.version`, complete host acceptance and retain the approved ZIP unchanged.
